**以后可采用的设计**

1. 安装前网络体检：默认只读，识别实际拥塞算法、实际 qdisc、缓冲区、内存/cgroup 限制、内存页大小、虚拟化、容器宿主机、XDP 和 TC 管理。已有调优应明确展示；不能只依据 default_qdisc 判定当前网卡队列。
2. 按需诊断：选择受控对端和近距离/跨境路径，分别测收发、单连接、多连接、重传和负载时延。设置总流量、速率、并发及运行时间上限，明确展示测试条件。
3. 候选参数预览：列出当前值、候选值和影响范围，区分测试 socket、协议进程、网络命名空间及整台服务器。按服务器管理共享参数，避免多个节点重复覆盖。
4. 对比与回滚：保存本轮涉及的原值，先建立独立本地超时恢复，再应用候选配置；交替比较基线与候选，检查管理连接和实际转发。失败、失联或无可靠收益时恢复，恢复后读回核验。
5. 报告与历史：同时记录吞吐、重传、资源、样本数、路径和测试预算，区分稳定改善、无明显变化、退化和结果不确定，不使用单一“优化分数”。

节点侧使用独立的按需脚本，不强制安装资源探针或常驻调优代理；分析、调度和历史记录放在面板。可复用现有管理通道，但不把测速异常接入节点自动重启条件。

默认不更换内核、不创建 swap、不改变 MTU/路由、不做全局整形，也不直接覆盖容器或平台管理的队列。连接级 pacing 可作为高级候选，但不能把某个对端测得的速率直接转换为全机限速。

**上游借鉴及适配条件**

参考 [tcpfit](https://github.com/Kylin010/tcpfit) 的计算、测试和恢复机制，以及 [iBytebox 调优方法](https://blog.ibytebox.com/posts/ai-agent-vps-tcp-tuning/) 的业务方向分析与对比流程。不能直接将上游全自动菜单嵌入安装步骤。

此前审阅的 tcpfit 0.5.9 默认以 150ms 估算 RTT，内存判断未读取 cgroup 限额、页数计算假设 4KiB，并需要补充 Alpine/OpenRC 持久化适配。真正实施时应重新审阅并固定版本、校验文件、保留许可，不能假设上游仍与本次审阅一致。

Reality 的 TCP 调整、Argo 的 HTTP/2 隧道连接、Hysteria2 的 UDP/QUIC 参数需要分开处理。不能把 Linux TCP BBR 参数直接当作 Hysteria2 传输层调优。

**重新启动方案的条件**

仅在用户明确要求加入相关功能时继续。先确认所需范围，再从只读体检和诊断入口开始；涉及参数应用时先小范围验证。后续 GitHub 发布仍依用户指示处理。

若继续研究本轮跨境问题，优先更换香港对端并分时段复测 US → HK 方向，区分线路与香港接收端因素，再决定是否需要参数调整。不要把尚未证实的路径瓶颈当成全局缓冲不足。
