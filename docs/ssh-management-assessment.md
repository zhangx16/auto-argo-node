# SSH 运维接入评估（原方案）

建议采用「轻量探针 + 可选 SSH 运维」，保留主动拉取模式作为另一种管理方式。此方案已按用户后续指令实现为面板功能，操作与验证范围见 [SSH 运维](ssh-operations.md)。首次真实服务器凭据由用户在网页录入；没有自动使用历史对话密码。

## 当前限制

管理脚本已以 root 运行，限制主要来自预设操作、定时轮询和缺少通用远程执行接口，不是 Shell 天生权限不足。SSH 能让管理员更灵活地操作服务器，但不能突破 LXC / Docker 的 capabilities、只读内核参数、宿主机资源限制或服务商策略；NAT 也不等同于权限受限，需分别探测虚拟化类型与权限。

代码已有 Paramiko SSH 连接、密码/私钥认证、主机密钥校验、超时和日志清理能力。当前 SSH 凭据在单次任务后清除；长期运维需要新增按服务器保存的凭据管理，而不能直接把原来的一次性部署接口当成长期任务系统。

## 角色分工

| 通道 | 职责 |
| --- | --- |
| Monitor 探针 | 心跳、资源、主机流量、协议进程及监听采样 |
| SSH 运维 | 服务/日志诊断、文件传输、部署卸载、核心与探针更新、管理员维护任务 |
| 面板转发探测 | 独立验证节点实际可用性，不能只根据 SSH 命令退出码判定成功 |
| 原主动拉取脚本 | SSH 不可达节点的管理通道，迁移期间保留回退能力 |

SSH 是按需连接，不保持所有服务器的常驻会话。不用 SSH 每秒采集资源，也不在节点安装 Python、Ansible 或额外常驻管理程序。现有 cron 脚本空闲时本来不常驻，迁移的主要收益是能力和可维护性；不能承诺明显减少节点内存。SSH 会话的峰值开销应在 Alpine / Debian、小内存容器上实测。

## 建议的数据和任务模型

- 凭据绑定服务器，节点绑定服务器；同机多个协议复用连接信息和操作锁。
- 保存地址/域名、端口、用户名、认证方式、固定主机指纹、管理方式及最近连通状态。DDNS 保留域名，每次连接重新解析；IP 变化不自动接受新主机密钥。
- 首次可用密码接入，为每台服务器生成独立管理密钥；私钥加密保存在面板，API 不回显，支持替换/撤销。已有手工 SSH 登录方式不自动关闭。
- 沿用持久任务队列，限制全局并发，同服务器互斥。任务有期限、步骤、结果、脱敏日志和验证状态。
- 文件通过 SFTP 流式传送，凭据写 root 专有临时文件，避免嵌入命令行或日志。上传后核对摘要、语法/配置，再原子替换。
- 连接中断后区分「未执行」「仍运行」「结果未知」。根据远端任务编号和结果文件恢复，不盲目重试重启、卸载等操作。
- 自动修复共用维护状态、授权计数、冷却和暂停策略；不能让 SSH 和 cron 同时修复同一节点。
- 主机密钥变化应停在指纹复核，适用于服务器重装或 DDNS 指向另一台机器。不能因为地址是域名就忽略校验。

## 迁移顺序

1. 服务器 SSH 接入、凭据更新、指纹展示、连接测试和只读诊断。按需提供日志、进程、监听、磁盘及系统权限检查。
2. 接入预设维护操作和现有升级/安装任务，保留转发验证、回滚和批次暂停。网页交互终端可后续单独评估。
3. 每台服务器先进入维护，确认无运行任务，验证 SSH，再关闭原管理 cron 并确认；最后切换自动修复执行方。探针采样和协议服务继续运行。SSH 验证失败不移除原通道。
4. 先覆盖一台 Debian KVM 和一台 Alpine NAT 容器，测试普通任务、SSH 断连、面板重启、DDNS 更新和失败回退，再推广。

面板集中保存高权限凭据后，面板本身成为重要管理边界，需要主机指纹固定、凭据不回显、操作日志和有界任务；不应以「关闭验证、跳过 SSH 错误」换取方便。新增 SSH 也不自动授权批量改内核、防火墙或网络参数，已保存的 TCP 调优方案继续暂缓。

参考：[OpenSSH sshd](https://man.openbsd.org/sshd.8)、[Docker 权限与隔离](https://docs.docker.com/engine/security/)。
